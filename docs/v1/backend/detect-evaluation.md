# 检测逐类别评测（合成语料，M0 证据）

状态：**回归与诊断证据，不是质量验收**。语料为合成、模板化，比真实办公材料容易得多；所有数值只说明实现链路（规则 + AstrLink Guard 经插件协议 + 位置映射）在受控输入下是否正确，不能当作发布门槛通过。需求 6.2 节要求的真实/授权去标识语料、独立测试集、冻结的置信区间规则与文档遗漏率上限均未具备。

## 做法

- 语料：`tools/m0_eval_corpus.py`（固定种子 20261031，确定性，两次生成摘要一致）。1,340 篇文档（80 个模板家族各 16 篇 + 60 篇负样本）、7,888 个实体、12 个类别。按模板家族划分开发 40 / 校准 16 / 测试 24（负样本另分），同家族不跨划分。标注只含敏感值本身，不含"电话："之类标签。
- 评测：`internal/detect/eval_test.go`，仅在设置 `TACET_EVAL_CORPUS` 与 `TACET_EVAL_REPORT` 时运行；经 `host.Start` 启动真实 AstrLink Guard int8（固定提交 7216b6a3）插件，对每篇文档跑完整 `detect.Service`，同一遍中分别统计仅规则、仅模型（分数 ≥ 0.8，上游建议值）与合并三种来源。结果见 `results/detect-eval-synthetic.json`（含 Wilson 95% 区间、按类别 / 子类 / 语言 / 划分的分项、误报与漏检样本）。
- 指标：精确片段（类别与起止都相同）P/R；完整覆盖召回（实体每个字符都落在某个候选内）；有实体文档的遗漏率；负样本文档出现候选的比例。单篇耗时 p50 8 ms、p95 11 ms（开发机，非 R1）。
- 规则包：`resources/rules/cn-office-v1.json`，经生产解析器 `rules.ParsePack`（拒绝未知成员与多余文档）加载；含手机、座机、邮箱、居民身份证（校验位，疑似保留）、银行卡（16/19 位，Luhn，疑似保留）、IPv4、URL、常见凭证格式，以及带上下文关键词的员工号与个人相关日期。评测另附一个仅用于评测的项目代号词典。

## 结果（合并来源，全部 1,340 篇；测试划分的数值在报告中，趋势一致）

| 类别 | 实体数 | 精确 P | 精确 R | 说明 |
| --- | ---: | ---: | ---: | --- |
| 手机 / 邮箱 / IP / URL / 凭证 / 项目 / 人名 | 各 288–1,696 | 1.000 | 1.000 | 合成数据上无误报漏检 |
| 居民身份证号 | 704 | 0.999 | 1.000 | 1 个 18 位订单号被疑似规则命中（带 validator_mismatch，应进复核） |
| 银行卡 | 416 | 1.000 | 1.000 | 规则 R=1.00；仅模型精确 R=0.66（完整覆盖 1.00，边界与卡号分隔写法不一致） |
| 地址 | 512 | 0.983 | 0.996 | 模型把"会议室 A302"等非地址当地址；1 个英文地址末尾偏移 |
| 日期（个人相关） | 240 | 0.956 | 1.000 | 模型把日志时间戳 `2026-09-30 14:05:12` 当日期；个人日期靠上下文规则补到 100% |
| 个人账号 / 员工号 / 微信号 | 544 | 0.796 | 1.000 | 精确率低的原因见下 |

合并后有实体文档的遗漏率在三个划分均为 0；60 篇负样本中 1 篇出现候选（模型把时间戳当日期）。各类别 95% 区间下限均在 0.98 以上，但样本都来自同一批模板，区间不含模板外的方差。

## 评测发现的问题

1. **员工号召回为 0，证件有效期日期召回 44%**（规则包最初只有格式规则，模型对这两类不敏感）。需求文档设计里的"上下文规则"在 `rules` 里并未实现。已实现 `Rule.Context` / `ContextWindow`（命中前方至多 N 个 code point、不跨换行内须出现关键词之一，大小写不敏感；窗口计入工作量预算；非法配置在编译期拒绝；`config` 的规则内容与 JSON Schema 同步），并为员工号与个人日期加规则，合并召回升到 100%。
2. **账号精确率 0.796**：模型把银行卡号同时标成 `account` 与 `payment_card`，同一片段两个类别。这是类别冲突，应由处置阶段按优先级消解（MD-12，task-7），检测层按设计保留全部候选。评测按类别精确匹配，因此被计为账号误报。
3. **模型误报**：非地址的"会议室 A302"、日志时间戳。负样本陷阱按设计起了作用；这些需要规则排除或阈值/类别策略，当前未处理。
4. **疑似规则**：18 位订单号形似身份证，校验失败，按设计带 `validator_mismatch` 进入复核而非静默丢弃。
5. **评测方法的教训**：我最初对上下文规则的"成本计入预算"测试并未区分有无计费（仅扫描量就已超预算），变异存活；改为"扫描量在预算内、加上回看成本才超出"并加无上下文对照后才抓住。

## 局限

- 语料合成、模板化、单一随机种子；未覆盖 OCR 错字、繁简体、罕见姓名之外的大量变体、长文档、跨 run / 跨块实体、数字存储类型、敏感键名。
- 没有校准：`Calibrated` 采用上游建议 0.8，不是 Tacet 的校准值；无人值守资格仍关闭。
- 上游 `bio-offset-consistency-v1` 与 IP/URL 清理契约未实现（见 m0-progress.md）。
- 没有真实办公文档、没有独立测试集、没有标注者一致性；"完整覆盖召回"只含本类别以外候选也算覆盖。
- 精确率按候选去重后统计，同一片段被规则与模型各报一次只计一次。
