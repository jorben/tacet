# 调度准入与任务持久化集成

状态：部分实现。本轮覆盖调度器的准入、执行循环与任务仓库组合，不代表实际进程树预算、完整插件流水线或 M0 已通过。

## 队列与资源准入

`internal/sched/queue.go` 用有上限的待派发视图和资源声明工作，StageRunner 由组装层注入。队列不导入实际格式、模型、业务阶段或 jobs；jobs 是持久化事实来源。

- 同时检查阶段的内存、CPU 槽、工作进程种类/数量、临时盘、候选盘、队列字节数及总并发；无效/超预算声明在提交时拒绝。
- 交互队列非空时只准入交互阶段；后台已执行阶段不被打断。相同优先级内优先推进发布、验证、导出、处置，再启动新抽取；同阶段按入队顺序。
- 后台不能使用为交互启动保留的内存余量。
- 已保留候选/检查点磁盘与执行阶段的临时预留分别计量。阶段结束不自动清掉存量占用；高水位阻止产生新数据的阶段，但允许验证和发布继续释放存量。
- 每张执行票据持有处理活动租约。取消请求不归还预算和租约，直到 runner 完成真正停止/进程回收后才释放；运行中的票据不能重复执行或提前 Finish。
- runner panic 或未知结果转换成稳定失败码，不传播异常值或声称成功。

声明预留不等于实际进程树测量/限制。目前 Budget 应由组装层扣除 UI/主进程、常驻模型和缓存开销；真实采样、Windows Job 内存上限、macOS 软阈值回收和压力降级序列仍待接入。

## 事件驱动执行循环

`internal/sched/dispatch.go` 提供 Dispatcher。提交/释放预算、暂停/继续、压力和磁盘状态变化以合并通知唤醒调度；外部网络租约释放后由调用方 Wake，不做定时准入轮询。

Dispatcher 只启动已经准入的有界阶段数。结果尚未被处理时仍计为活动执行，避免通知唤醒让完成消息积压。Completion 回调串行执行并可以提交后续阶段；提交错误会停止新派发、取消活动阶段并排空它们的最终结果。关闭时不强制丢弃未完成计算，runner 负责任务取消/进程树回收。

Cancel 精确针对 AttemptRef，移除排队阶段或通知正在执行的 context。调度器不替 jobs 写入取消/暂停状态；用户命令须在 workspace 中持久化状态并使旧 attempt 失效。

## 测试证据

队列测试独立压低每个预算维度以验证没有超额准入，覆盖交互阻塞不能被小后台请求绕过、下游优先、高水位、存量磁盘、不允许提前释放票据、租约互斥、未知结果/panic 和取消。

Dispatcher 测试覆盖暂停后恢复唤醒、完成回调入队下一阶段、活动阶段取消后仍占预算直至返回、持久化失败停止并排空活动任务，以及外部网络租约释放后的唤醒。

`internal/jobs/scheduler_integration_test.go` 用真实文件 SQLite、workspace.AdmitTx、任务仓库与 Dispatcher 组合。三个可控 runner 依次完成预检、抽取和处置，批次确认后自动推进至 awaiting_review；检查三条阶段记录和最终状态持久化，复核等待时没有工作进程预留或处理租约。这个测试证明编排，不是文件解析/检测能力。

```sh
go test -race -count=1 -timeout=25s ./internal/sched ./internal/jobs ./internal/workspace ./internal/store ./internal/archtest
```

## 快照版本变更的失效（task-5 增量）

**缺口与处理**：`lineage`（失效判定）与 `snapshot.NewVersion`（分面差异）此前各自有实现和测试，但 `jobs` 没有保存阶段读取了什么，也没有任何调用方，所以“配置变了，已有结果是否还能用”没有被落实。

**记录**：`jobs_stage` 增加 `output`（完成的运行产生的任务版本，0 表示未完成）与 `reads`（JSON：输入指纹、决定版本、补充词版本、所读分面摘要、所消费的上游输出）。`BeginStageReading` 在阶段开始的同一事务里写入，上游输出取自该任务已完成的最新运行。`BeginStage` 保持原样，用它开始的运行没有读取记录，之后的比较一律视为失效。

**`ApplySnapshotChange(batch, expected, version, facets)`**：同一事务内 ① 绑定新版本（版本不增或期望值不符则整体拒绝）② 分页遍历成员：已完成阶段按 `lineage.EarliestStale` 判定，只比较配置分面（输入/决定/补充词取自各记录自身，因为此处只有配置变了）；正在运行的尝试若所读分面与新值不同则从其阶段重启（尝试被作废，迟到结果拒绝）。补充扫描没有任务状态，失效时从抽取重启（更早，更安全）。草稿、取消中、终态成员不动。结果返回受影响成员及其重启阶段；调用方在提交后取消正在运行的工作。

**状态机修正**：`EvInvalidate` 原来对任何非草稿状态都置为排队，这会：把用户暂停的任务悄悄恢复运行；绕过密码、输入变化、资源、目标阻塞；让失败的任务自动重新运行。现在：暂停保持暂停并把恢复点移到失效阶段；阻塞保持阻塞只把游标前移；失败保持失败并把重处理起点前移到不晚于失效阶段；其余状态回到排队。

**测试**：见 `jobs/invalidate_test.go`、`transition_test.go`。变异：运行中尝试被忽略、输入也参与比较、完成运行不记录输出、不绑定版本、终态与取消中成员被触动、暂停被覆盖、阻塞被绕过、失败重处理起点后移或自动重启、补充扫描未映射，均被抓住。

**局限**：发布阶段不因交付分面变化而重启（已发布的交付按设计只被替代，不被失效；进行中的发布不在此处理）；运行中尝试的“取消正在运行的工作”由调用方在提交后执行，本层只作废尝试；`Input`、`Decisions` 的当前值何时变化（输入指纹校验、`review` 决定提交）由其所有者通过 `EvInputChanged`、`EvDecisionsChange` 驱动，不经此函数；没有 `app` 层的“修改配置→冻结新快照→ApplySnapshotChange”用例，也没有 GUI 的确认提示；批次内大量成员（数万）的耗时未测。

## 阶段内检查点（task-5 增量）

设计（模块设计 5.3、FR-05）：声明大文件能力的插件在阶段内保存检查点，暂停或崩溃后继续时作为输入交给新尝试；其他插件丢弃本次尝试、重做阶段。`jobs` 此前只丢弃尝试，没有检查点记录。

`jobs_checkpoint(job, stage, attempt, seq, ref, reads)`，每作业每阶段一条。`SaveCheckpoint(attempt, ref, seq)` 只接受当前作业版本的当前运行尝试，且 `seq` 必须大于已有值，所以被丢弃或迟到的尝试覆盖不了新尝试依赖的检查点，也不会倒退到已提交的位置。`TakeCheckpoint(job, stage, reads)` 只在输入指纹和该阶段所依赖的分面摘要都与保存时一致时返回；否则删除并从头开始，过期的检查点不会被交出。阶段 `Completed` 后删除该阶段的检查点；取消完成（用户取消或恢复时完成取消）后删除该作业全部检查点。暂停与恢复保留。

验证：`jobs/checkpoint_test.go`。变异：序号相等被接受、任意尝试可保存、不比较输入、不比较分面、过期检查点保留、完成后不清除、取消后不清除、恢复完成取消后不清除、取出时忽略阶段，均被抓住。

局限：检查点指向的产物由谁写、如何读回、占用如何计入 `sched` 的存储计量（PF-17 中的"检查点"类别）都属于抽取检测阶段与存储计量，尚未实现；`jobs` 只保存引用和序号，不验证引用的产物是否存在或完整；清除检查点引用时，对应产物文件的删除由 `retention`/`refs.Purge` 负责，没有联动；没有对"保存检查点与提交文本单元在同一事务"这一设计要求做跨模块验证（文本单元模块尚不存在）。
